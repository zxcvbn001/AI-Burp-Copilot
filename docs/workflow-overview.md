# AI Burp Copilot v2 工作流总览

单独的流程图见：[AI 工作流流程图](ai-workflow-flowchart.md)。

## 1. 项目目标

AI Burp Copilot v2 的目标，不是简单做一个“AI 被动扫描器”，也不是替代 Burp 自带扫描能力，而是把真实经过 Burp 的 HTTP 流量，转化为一个可分析、可验证、可追踪、可复核的安全分析流程。

它的核心设计思路是：

- 以 Burp 真实流量为入口
- 以规则为中心定义能力边界
- 以工作流串联“分析 -> 判断 -> 验证 -> 聚合”
- 以 LLM 辅助理解业务语义和响应差异
- 以 UI 展示中间过程和最终结果

---

## 2. 整体流程

一个请求进入插件后，会经历下面几个阶段：

1. 流量采集
2. 基础过滤与分类
3. AI 分析攻击面
4. 提取候选参数与候选漏洞类型
5. 参数影响性判断
6. 基于规则的验证发包
7. 本地规则判定 + LLM 差异复核
8. 聚合为最终漏洞结论
9. 写入历史与 UI 展示

可以概括为：

```text
Burp 流量
  -> 接口识别
  -> AI 分析
  -> 候选参数提取
  -> 参数影响性判断
  -> 规则验证
  -> LLM 复核
  -> 漏洞聚合
  -> UI 展示
```

---

## 3. 各模块职责

## 3.1 流量采集模块

职责：

- 接收 Burp Proxy 中经过的请求与响应
- 提取请求方法、URL、参数、请求体、响应体等上下文信息
- 构造统一的分析对象，供后续模块处理

价值：

- 所有分析都建立在真实流量基础上
- 不依赖“凭空生成请求”
- 便于后续复现、回放和人工确认

---

## 3.2 Pipeline 编排模块

职责：

- 负责把一个请求按固定阶段顺序处理
- 控制每一步什么时候执行、什么时候跳过
- 保证整个分析链条可以统一运行

价值：

- 把复杂流程拆成稳定的阶段
- 每个阶段职责单一，便于调试、扩展和替换

---

## 3.3 Endpoint 分析模块

职责：

- 识别当前流量是业务接口还是静态资源
- 对业务接口做攻击面分析
- 对静态资源做单独扫描

价值：

- 避免把所有流量一视同仁
- 让接口分析和静态文件分析分开处理
- 降低无效扫描和误判

---

## 3.4 AI 分析模块

职责：

- 分析接口用途与业务语义
- 找出高价值参数
- 输出潜在漏洞类型
- 输出建议验证方向

LLM 在这里的定位不是“直接断定漏洞”，而是：

- 帮助理解接口
- 帮助识别参数的业务意义
- 帮助决定后续验证重点

价值：

- 提高对业务接口的理解能力
- 避免完全依赖简单关键字或固定规则

---

## 3.5 规则引擎

职责：

- 定义每类漏洞有哪些验证规则
- 定义规则适用于哪些参数类型和值类型
- 定义如何构造最小化探测请求
- 定义本地如何判断探测结果

规则不是一个“补丁模块”，而是插件能力的中心。

规则贯穿：

- 支持哪些漏洞类型
- 每个漏洞怎么验证
- 验证时允许哪些策略
- 哪些场景需要 LLM 复核

价值：

- 可扩展
- 可控
- 可审计
- 不需要每次新增漏洞都修改大量 Java 代码

---

## 3.6 参数影响性判断模块

职责：

- 判断参数是否真正参与服务端业务语义
- 避免对明显无意义参数做后续验证

这里的设计重点不是简单比较“响应有没有变化”，而是综合判断：

- 参数是否改变了请求含义
- 参数是否影响业务对象选择、权限、查询或写入行为
- 参数变化是否带来了可解释的服务端差异
- 是否需要 LLM 辅助理解业务影响

价值：

- 降低误报
- 减少无效发包
- 提升验证资源利用率

---

## 3.7 验证工作流模块

职责：

- 把候选漏洞按固定流程执行验证
- 先判断参数是否值得测
- 再按照规则逐个发起 probe
- 再对响应做本地判定与 LLM 复核

每次验证都尽量遵循：

- 最小化修改参数
- 可回放
- 可记录
- 可解释

价值：

- 让验证过程标准化
- 同一个漏洞类型可以不断完善规则，而不用重写整体流程

---

## 3.8 LLM 二次研判模块

职责：

- 对响应差异做语义复核
- 对规则命中的证据做合理性判断
- 在最终漏洞聚合后做一次结果复核

当前系统里，LLM 主要承担两类复核：

1. Probe 级复核  
   针对单次验证过程，看差异是否真的支持该漏洞

2. Finding 级复核  
   针对最终聚合结果，再做一次整体确认

价值：

- 弥补纯相似度/纯规则判断的局限
- 尤其适合业务差异较弱、但语义上有风险的场景

---

## 3.9 Finding 聚合模块

职责：

- 将多条验证证据聚合成一个更稳定的“最终漏洞结论”
- 从中间验证记录中筛出真正有价值的结果

价值：

- 区分“探测记录”和“最终漏洞”
- 让最终输出更适合人工确认和汇报

---

## 3.10 UI 展示模块

当前 UI 主要用于展示不同层级的信息：

- 历史：所有分析记录
- Endpoint 分析：接口级分析结果
- 参数分析：参数影响性判断结果
- 漏洞验证过程：每次验证的完整请求/响应/差异
- 有效漏洞：聚合后的最终漏洞结论
- 日志：系统、LLM、验证过程日志
- 设置：配置、规则、Prompt 的加载与调整

价值：

- 中间结果可见
- 最终结论可追溯
- 便于定位问题和持续迭代

---

## 4. 规则与 LLM 的分工

规则和 LLM 的边界应该明确：

### 规则负责什么

- 定义系统能做哪些验证
- 定义验证请求如何构造
- 定义本地判断的基础标准
- 决定是否需要额外 LLM 复核

### LLM 负责什么

- 理解接口和参数的业务意义
- 理解响应差异的语义含义
- 帮助判断“差异是否真的支持某类漏洞”

### 这两者为什么必须结合

只有规则：

- 稳定，但容易死板
- 容易误判业务弱差异场景

只有 LLM：

- 灵活，但不够可控
- 难以直接作为验证引擎

组合后的目标是：

- 规则保证可控、可重复
- LLM 提升理解能力和判断上限

---

## 5. 当前架构的核心设计价值

当前项目最重要的设计价值，不在于“多支持几种漏洞”，而在于已经具备了以下能力雏形：

- 以真实流量驱动分析
- 以规则驱动验证
- 以工作流驱动执行
- 以 LLM 辅助语义判断
- 以最终聚合输出稳定结论
- 以 UI 展示完整过程

这意味着项目已经从“零散功能点”走向“可持续演进的验证平台”。

---

## 6. 当前仍需持续完善的方向

虽然整体链路已经成型，但仍有几个重点方向需要继续加强：

- 进一步统一规则、工作流、UI 之间的状态表达
- 继续降低参数影响性判断误差
- 继续完善最终有效漏洞的聚合和二次研判体验
- 增强更多漏洞类型的规则库
- 提升去重、稳定性、配置热加载和日志可观测性

---

## 7. 一句话总结

AI Burp Copilot v2 当前已经不是一个“单点 AI 插件”，而是一个围绕 Burp 流量、规则验证、LLM 复核和结果聚合构建的安全分析工作流平台。
